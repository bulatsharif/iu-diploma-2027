# Процедура экспериментов

Документ описывает замеры одного фиксированного деплоя: целевой модели, выбранного чекпоинта драфтера (либо без драфтера) и настроек сервинга. Все прогоны и таблицы ниже относятся к этому деплою. При смене конфигурации результаты заполняем отдельно.

### Конфигурация деплоя

- GPU: 1 × H100; целевая модель: `Qwen/Qwen3-8B`, локально `models/Qwen3-8B`.
- `dtype`: BF16 (`--dtype bfloat16`). CUDA graphs, лимиты батчинга и остальные параметры сервинга — по умолчанию.
- Драфтер: указываем один выбранный чекпоинт или `без драфтера`. Для исходного [`z-lab/Qwen3-8B-DFlash-b16`](https://huggingface.co/z-lab/Qwen3-8B-DFlash-b16#vllm) используем `--speculative-config '{"method":"dflash","model":"z-lab/Qwen3-8B-DFlash-b16","num_speculative_tokens":15}'`, как в карточке чекпоинта. В деплое без драфтера этот параметр не передаём.
- Prefix caching отключён: `--no-enable-prefix-caching`.
- Имя модели в API: `--served-model-name qwen3-8b`.
- Параметры генерации — по умолчанию модели/vLLM; EOS и stop-параметры не переопределяем. Длину ответа задаём системной инструкцией.
- Для метрик принятия включаем `--per-request-spec-decode-metrics summary`.


### Данные

- Русские запросы из WildChat
- Английские запросы из WildChat


К этим запросам добавляем системные промпты из `data/system_prompts`, задающие целевую длину ответа около 100, 500 или 1000 токенов. Полный вход, включая системный промпт, всю историю и chat template Qwen3, должен занимать 70–130 токенов. Thinking отключён (`enable_thinking=false`). Получаем такие профили:

- Префилл: ≈ 100 токенов
- Декод: ≈ 100, 500, 1000 токенов

Подготовка запросов из корня проекта:

```bash
.venv/bin/python scripts/prepare_wildchat_prompts.py
```

Скрипт читает первый Parquet-файл публичного [allenai/WildChat-1M](https://huggingface.co/datasets/allenai/WildChat-1M), около 231 MB. Файл сохраняется в кэш Hugging Face; весь датасет не скачивается. Версия датасета зафиксирована в скрипте. Прокси отключается только для процесса скрипта. Для чтения Parquet используется `pyarrow`, уже установленный в `.venv`; при необходимости установить: `uv pip install --python .venv/bin/python pyarrow`.

Отбираются первые 100 уникальных подходящих историй на каждом языке. История сохраняется до последнего сообщения пользователя включительно; последующий ответ из датасета не входит в запрос. Язык проверяется по разметке диалога и последнего сообщения пользователя.

Один и тот же набор из 100 запросов на язык должен укладываться в 70–130 токенов со всеми тремя системными промптами. Результат — шесть файлов `data/prompts/{ru,en}_{100,500,1000}.jsonl` в формате AIPerf `raw_payload`. Каждая строка — готовое тело запроса `/v1/chat/completions`: `model`, `messages` с системной инструкцией, streaming с usage и `enable_thinking=false`. Источник, параметры отбора, ID исходных диалогов и длины входов записываются в `data/prompts/metadata.json`; записи для каждого языка идут в том же порядке, что строки JSONL. Фильтрация проверяет длину входа; длина будущего ответа задаётся инструкцией и может отклоняться от цели.

### Инструмент замера

В качестве фреймворка для сервинга LLM будем использовать `vllm`, версия `0.30.0`. Для замеров скорости будем использовать `AIPerf`, версия `0.13.0`. Будем замерять при следующих нагрузках:
- `concurrency=1`. То есть в полете всегда только один запрос
- `RPS=1`
- `RPS=2`
- `RPS=4`
- `RPS=8`
- `RPS=16`

В режиме RPS используем пуассоновский поток (`--arrival-pattern poisson`). Режим `concurrency=1` запускаем отдельно, без ограничения RPS. Каждый язык и каждый профиль длины измеряем отдельно.

Во всех режимах держим разминку 30 секунд, затем подаём основную нагрузку 120 секунд. Таймаут запроса и `benchmark_grace_period` оставляем по умолчанию. После 120 секунд новые запросы не отправляются, но ответы, полученные в течение grace period (по умолчанию 30 секунд), входят в итоговые метрики AIPerf. Это 120 секунд подачи нагрузки, а не строгий срез метрик по 120-й секунде; см. [описание параметров AIPerf 0.13.0](https://github.com/ai-dynamo/aiperf/blob/v0.13.0/docs/cli-options.md#--benchmark-grace-period-float).

Установка зависимостей в существующее окружение:

```bash
uv pip install --python .venv/bin/python -r requirements.txt
```

В первом терминале запускаем модель без драфтера и ждём готовности сервера:

```bash
bash scripts/serve_baseline.sh
```

По умолчанию используется GPU 0; другой GPU можно выбрать через `CUDA_VISIBLE_DEVICES`. Сервер остаётся запущенным на время всех замеров.

Во втором терминале можно запустить один профиль:

```bash
bash scripts/benchmark.sh ru_100 rps 1
bash scripts/benchmark.sh en_500 concurrency 1
```

Аргументы: профиль `{ru,en}_{100,500,1000}`, режим `rps` или `concurrency`, значение нагрузки. Необязательный четвёртый аргумент — каталог результатов; по умолчанию создаётся каталог с датой и параметрами прогона внутри `results/`. Адрес сервера по умолчанию — `http://localhost:8000`, переопределяется через `BENCHMARK_URL`.

Для всей сетки нагрузок и сборки трёх таблиц запускаем:

```bash
.venv/bin/python scripts/run_benchmarks.py
```

Скрипт последовательно выполняет 36 прогонов одного уже запущенного деплоя: 2 языка × 3 длины × (`concurrency=1` и RPS 1, 2, 4, 8, 16). Это около 90 минут подачи нагрузки и разминки, плюс запуск AIPerf и ожидание ответов. Все прогоны используют 30 секунд разминки и 120 секунд основной нагрузки.

Другие значения нагрузки и каталог результатов можно задать явно:

```bash
.venv/bin/python scripts/run_benchmarks.py --rps 1 2 4 --concurrency 1 2 --output-dir results/baseline
```

Каталог для всей серии должен быть новым. Итог — `results/<дата>/tables.md` с тремя таблицами и отдельные каталоги прогонов с исходными отчётами AIPerf, включая `profile_export_aiperf.json`. Таблицы обновляются после каждого успешного прогона. TPOT берём из `inter_token_latency`; длину ответа — из `output_sequence_length`. Без драфтера метрики принятия отмечаются `—`.

`benchmark.sh` передаёт AIPerf один JSONL-файл в [формате raw payload](https://github.com/ai-dynamo/aiperf/blob/v0.13.0/docs/tutorials/raw-payload-replay.md), включает streaming и использует серверные счётчики токенов.

### Логируемые метрики

Для каждого прогона выбранного деплоя с заданным языком, нагрузкой и профилем длины будем логировать:

- Режим нагрузки: `concurrency=1` или заданный RPS.
- TTFT, TPOT и Latency: p50, p95, p99, в миллисекундах.
- Output tokens/s: суммарная скорость выдачи токенов сервером.
- Фактическую длину ответа в токенах: p50, p95, p99.
- Acceptance Rate: доля принятых draft-токенов, %.
- Acceptance Length: среднее число токенов за проверку, включая бонусный токен целевой модели.

Число токенов берём из серверного `usage`. AIPerf получает метрики принятия из ответа vLLM; без драфтера эти поля отсутствуют. Для итогов прогона используем `spec_decode_overall_draft_acceptance_rate` и `spec_decode_token_weighted_acceptance_length` — отношения суммарных счётчиков, а не среднее процентов по запросам.

Для TTFT, TPOT, Latency и фактической длины ответа указываем p50/p95/p99 в одной ячейке через слеш, в этом порядке. Output tokens/s, Acceptance Rate и Acceptance Length содержат по одному значению за прогон. `…` означает результат, который предстоит измерить. Для деплоя без драфтера в Acceptance Rate и Acceptance Length ставим `—`.
